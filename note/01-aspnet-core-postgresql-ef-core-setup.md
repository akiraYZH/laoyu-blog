# ASP.NET Core 接入 PostgreSQL 前，先搞懂 EF Core、Npgsql 与 Migration

很多 ASP.NET Core 教程会先用一个静态 `List<T>` 演示 Controller：代码简单、接口马上能返回 JSON，也不需要准备额外环境。

但一旦开始开发真正的博客、商城或用户系统，内存列表很快就不够用了。应用重启后数据会丢失，多个服务实例无法共享数据，也没有事务、索引和数据库约束。此时就需要把数据放进真正的数据库。

“接入 PostgreSQL”听起来像安装一个包，实际涉及多个职责完全不同的组件：

- PostgreSQL Server；
- EF Core；
- Npgsql Provider；
- EF Core Migration；
- `dotnet-ef` 命令行工具；
- 可选的 Docker 运行环境。

如果没有先分清它们的边界，很容易产生几个疑问：安装了 Npgsql，为什么还要运行 PostgreSQL？PostgreSQL 可以执行 `ALTER TABLE`，为什么还需要 Migration？`dotnet-ef` 为什么不直接写进 `.csproj`？

本文先回答这些问题，再完成 .NET 10 项目的 EF Core 工具链配置。数据库容器、连接字符串和 `DbContext` 将留到后续步骤。

## 从内存列表到持久化数据库

一个用于演示的 Controller 可能包含这样的代码：

```csharp
private static readonly List<Blog> Blogs =
[
    new() { Id = 1, Title = "Hello ASP.NET Core" },
    new() { Id = 2, Title = "Hello PostgreSQL" }
];
```

这种写法不是数据库，只是当前应用进程中的一个 C# 对象。它存在几个明显限制：

- 应用重启后，运行期间新增的数据会消失；
- 多个应用实例各自持有一份列表；
- 无法依赖数据库事务保证一组操作同时成功或失败；
- 没有唯一约束、外键、索引等关系数据库能力；
- 数据量增加后，筛选、排序和分页都需要应用自己处理。

接入 PostgreSQL 后，数据流会变成：

```text
HTTP Request
    ↓
Controller
    ↓
DbContext / EF Core
    ↓
Npgsql Provider
    ↓
PostgreSQL Server
    ↓
磁盘或 Docker Volume
```

理解这条链路，是后续配置的基础。

## PostgreSQL：真正保存数据的服务器

PostgreSQL 是一个独立运行的关系数据库服务器。它负责：

- 创建数据库、Schema 和数据表；
- 执行 SQL；
- 保存、查询和更新数据；
- 管理事务、锁和并发；
- 提供主键、外键、唯一约束和检查约束；
- 使用索引优化查询；
- 把数据持久化到存储介质。

ASP.NET Core 应用最终必须连接到一个正在运行的 PostgreSQL Server，例如：

```text
Host=localhost;
Port=5432;
Database=blog;
Username=blog_user;
Password=development_password;
```

这里的 `localhost:5432` 必须真的有 PostgreSQL 在监听。仅仅安装一个 NuGet 包，不会自动产生数据库服务器。

## Npgsql：EF Core 与 PostgreSQL 之间的适配层

`Npgsql.EntityFrameworkCore.PostgreSQL` 经常被笼统地称为“PostgreSQL 驱动”，但更准确的名称是 **PostgreSQL 的 EF Core Provider**。

它建立在底层 Npgsql ADO.NET Driver 之上，负责让 EF Core 理解 PostgreSQL 的连接方式、数据类型和 SQL 方言。

例如应用写下：

```csharp
var blogs = await db.Blogs
    .OrderByDescending(blog => blog.CreatedAt)
    .ToListAsync();
```

EF Core 会分析 LINQ 表达式，Npgsql Provider 再生成 PostgreSQL 能执行的 SQL。简化后类似：

```sql
SELECT "Id", "Title", "CreatedAt"
FROM "Blogs"
ORDER BY "CreatedAt" DESC;
```

Npgsql Provider 负责连接和翻译，但不负责保存数据。可以把它理解为翻译员：翻译员知道双方如何交流，但翻译员本身不是数据库。

因此，完整关系是：

```text
EF Core
    负责模型、查询和实体状态

Npgsql Provider
    负责把 EF Core 操作转换为 PostgreSQL 操作

PostgreSQL Server
    负责执行 SQL 并持久化数据
```

## Docker：运行 PostgreSQL 的一种方式

Docker 既不是数据库，也不是数据库驱动。它只是 PostgreSQL Server 的一种运行环境。

本地开发通常有三种选择：

| 方案 | PostgreSQL 运行在哪里 | 是否需要本机 Docker |
|---|---|---:|
| 原生安装 | macOS、Windows 或 Linux 系统服务 | 否 |
| Docker | PostgreSQL 容器 | 是 |
| 云数据库 | AWS RDS、Supabase、Neon 等 | 否 |

选择 Docker 的常见原因包括：

- 不把 PostgreSQL 直接安装到开发机；
- 可以固定数据库版本；
- 可以快速启动、停止和重建环境；
- 使用 Volume 保存容器外的数据；
- 团队成员更容易获得一致的开发环境；
- 本地 Compose 配置可以自然过渡到服务器环境。

所以，“安装 Npgsql 后为什么还要 Docker”的答案是：

> Npgsql 让应用能够连接 PostgreSQL；Docker 用来运行 PostgreSQL 本身。

如果已经有可连接的 PostgreSQL Server，就不必为了 Npgsql 再使用 Docker。

## PostgreSQL 能改表，为什么还需要 Migration

PostgreSQL 原生支持数据库结构变更。例如创建表：

```sql
CREATE TABLE "Blogs" (
    "Id" integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    "Title" text NOT NULL
);
```

后续增加字段：

```sql
ALTER TABLE "Blogs"
ADD COLUMN "CreatedAt" timestamp with time zone NOT NULL;
```

这说明 PostgreSQL 具备执行 Schema 变更的能力，但它并不知道应用代码发生了什么变化。

假设 C# 实体从：

```csharp
public class Blog
{
    public int Id { get; set; }
    public required string Title { get; set; }
}
```

变成：

```csharp
public class Blog
{
    public int Id { get; set; }
    public required string Title { get; set; }
    public DateTime CreatedAt { get; set; }
}
```

PostgreSQL 不会主动读取 C# 类，也不会自动判断应该增加 `CreatedAt` 字段。它更不会替应用管理以下问题：

- 哪些结构变更已经执行；
- 多个变更应该按什么顺序执行；
- 开发、测试和生产数据库分别处于哪个版本；
- 新开发者如何恢复相同的数据库结构；
- 如何把数据库结构变化纳入代码审查和版本控制。

EF Core Migration 提供的正是这套应用级管理流程：

```text
修改实体模型
    ↓
EF Core 对比当前模型与历史快照
    ↓
生成 Migration 文件
    ↓
Npgsql Provider 生成 PostgreSQL SQL
    ↓
PostgreSQL 执行结构变更
    ↓
__EFMigrationsHistory 记录已执行版本
```

PostgreSQL 仍然是结构变更的最终执行者，EF Core Migration 则负责生成、组织和追踪这些变更。

不使用 EF Core Migration 也完全可行。开发者可以手写：

```text
migrations/
├── 001_create_blogs.sql
├── 002_add_created_at.sql
└── 003_add_author_id.sql
```

但执行顺序、历史记录、重复执行保护和团队同步都需要自己管理，或者交给 Flyway、Liquibase、DbUp 等专门工具。

另外，PostgreSQL 的 `pg_upgrade` 处理的是 PostgreSQL Server 大版本升级，例如 PostgreSQL 17 升级到 18；它和应用数据表的 Migration 不是同一个概念。

## 为 .NET 10 安装 Npgsql Provider

在 ASP.NET Core 项目目录运行：

```bash
dotnet add package Npgsql.EntityFrameworkCore.PostgreSQL
```

这条命令会：

1. 从 NuGet 获取 Npgsql EF Core Provider；
2. 把依赖写入当前项目的 `.csproj`；
3. 恢复该包所需的间接依赖。

项目文件会出现类似配置：

```xml
<PackageReference
  Include="Npgsql.EntityFrameworkCore.PostgreSQL"
  Version="10.0.3" />
```

这里最重要的是主版本兼容性：使用 EF Core 10 的项目，应选择兼容 EF Core 10 的 Npgsql Provider。复制命令到其他项目时，应重新核对当前稳定版本，而不是盲目照搬示例中的补丁版本。

完成这一步后，项目获得了通过 EF Core 访问 PostgreSQL 的能力，但还没有连接任何数据库。

## 安装 EF Core Design 包

接着安装 EF Core 的设计时依赖：

```bash
dotnet add package Microsoft.EntityFrameworkCore.Design
```

`.csproj` 中会出现类似内容：

```xml
<PackageReference Include="Microsoft.EntityFrameworkCore.Design" Version="10.0.10">
  <IncludeAssets>runtime; build; native; contentfiles; analyzers; buildtransitive</IncludeAssets>
  <PrivateAssets>all</PrivateAssets>
</PackageReference>
```

这个包主要服务于开发阶段：

- 发现和创建 `DbContext`；
- 分析实体模型；
- 生成 Migration；
- 配合工具更新数据库结构。

`PrivateAssets` 设置为 `all`，表示它不应该作为传递依赖暴露给引用当前项目的其他项目。

## 为什么 dotnet-ef 不属于普通 PackageReference

到这里还不能直接假定终端拥有 `dotnet ef` 命令，因为项目依赖和 CLI 工具是两类东西。

```text
Microsoft.EntityFrameworkCore.Design
    → 项目中的设计时依赖

dotnet-ef
    → 在终端运行的 .NET Tool
```

普通 NuGet Library 由 C# 项目引用，因此写进 `.csproj`。`dotnet-ef` 是独立命令行程序，应该由 .NET Tool 系统管理。

## 为什么优先使用 Local Tool

`dotnet-ef` 可以全局安装：

```bash
dotnet tool install --global dotnet-ef
```

但 Global Tool 属于开发者个人环境，项目本身不会记录工具版本。不同开发者可能使用不同版本，CI 环境也需要额外配置。

Local Tool 会把工具和版本记录在项目的 Tool Manifest 中：

| 对比项 | Global Tool | Local Tool |
|---|---|---|
| 作用范围 | 当前用户的所有项目 | 当前目录及其子目录 |
| 版本是否跟随项目 | 否 | 是 |
| 新环境恢复方式 | 手动安装 | `dotnet tool restore` |
| 适合场景 | 通用个人工具 | 项目构建和 Migration 工具 |

对于 Migration 工具，Local Tool 通常更容易复现。

## 创建 Tool Manifest

在项目根目录运行：

```bash
dotnet new tool-manifest
```

命令会创建 `dotnet-tools.json`。根据 SDK 和现有目录结构，它可能位于项目根目录，也可能位于 `.config` 目录；应以命令实际生成的位置为准。

一个空 Manifest 类似：

```json
{
  "version": 1,
  "isRoot": true,
  "tools": {}
}
```

其中 `isRoot: true` 表示 .NET SDK 搜索 Local Tool 时，不再继续向更高层目录查找其他 Manifest。

## 在项目中安装 dotnet-ef

如果 Manifest 位于项目根目录，可以明确指定它：

```bash
dotnet tool install dotnet-ef \
  --version 10.0.10 \
  --tool-manifest ./dotnet-tools.json
```

安装完成后，Manifest 会记录工具版本和命令：

```json
{
  "version": 1,
  "isRoot": true,
  "tools": {
    "dotnet-ef": {
      "version": "10.0.10",
      "commands": [
        "dotnet-ef"
      ],
      "rollForward": false
    }
  }
}
```

`rollForward: false` 表示工具不会自动改用另一个版本。项目的 Migration 行为因此更容易保持一致。

其他开发者取得代码后，不必重新研究应该安装哪个版本，只需运行：

```bash
dotnet tool restore
```

## 验证项目级 dotnet-ef

首先列出当前目录可用的 Local Tool：

```bash
dotnet tool list --local
```

输出应包含工具版本和 Manifest 位置：

```text
Package Id   Version   Commands    Manifest
dotnet-ef    10.0.10   dotnet-ef   ./dotnet-tools.json
```

然后明确通过 Local Tool 机制执行：

```bash
dotnet tool run dotnet-ef --version
```

预期输出：

```text
Entity Framework Core .NET Command-line Tools
10.0.10
```

这里使用完整形式 `dotnet tool run dotnet-ef`，是为了明确验证项目级工具，避免和个人环境中可能存在的 Global Tool 混淆。

如果曾经误装过 Global Tool，可以先确认 Local Tool 正常，再移除全局版本：

```bash
dotnet tool uninstall --global dotnet-ef
```

## 此时数据库还没有出现

完成上述配置后，项目拥有了：

- PostgreSQL 的 EF Core Provider；
- EF Core 设计时服务；
- 可复现的项目级 `dotnet-ef` 工具。

但此时仍然没有：

- 正在运行的 PostgreSQL Server；
- 数据库连接字符串；
- 实体与 `DbContext`；
- Migration 文件；
- PostgreSQL 数据表。

工具链准备完成，不等于数据库接入完成。接下来的正确顺序是：

```text
用 Docker Compose 启动 PostgreSQL
    ↓
验证数据库健康状态
    ↓
配置开发环境连接字符串
    ↓
创建实体和 DbContext
    ↓
在依赖注入容器中注册 DbContext
    ↓
生成并应用第一个 Migration
    ↓
把 Controller 的内存列表替换为数据库查询
```

## 总结

ASP.NET Core 接入 PostgreSQL 不是简单地“安装数据库驱动”。它由多个各司其职的组件共同完成：

- PostgreSQL Server 负责执行 SQL 和保存数据；
- EF Core 负责对象映射、查询表达和实体状态；
- Npgsql Provider 负责连接 PostgreSQL 并适配其 SQL 与类型系统；
- EF Core Migration 负责生成和追踪应用结构变化；
- `dotnet-ef` 提供 Migration 命令；
- Docker 只是运行 PostgreSQL Server 的一种可选方式。

先把这些边界理清，再配置数据库容器、连接字符串和 `DbContext`，后续遇到连接失败或 Migration 异常时，就能快速判断问题到底发生在哪一层。
